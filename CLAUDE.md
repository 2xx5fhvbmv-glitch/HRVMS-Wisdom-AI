# HRVMS-Wisdom-AI — Architecture & Working Rules

Read this file fully before starting ANY task in this repo. It exists so every session (yours or a future one) has the same context instead of re-discovering it turn by turn. Update it whenever you learn something here was wrong or incomplete — don't let it go stale.

## What this project is

HR / Workforce Management system for Maldives resorts, multi-tenant (one resort = one `resort_id`). Covers the full employee lifecycle: onboarding, time & attendance, duty rosters, leave, island pass (inter-island travel approval), payroll & salary advances, benefit grids (rank-based compensation policy), performance reviews, grievance & disciplinary, incidents, accommodation/maintenance requests, visa/document management, survey, learning & development, workforce planning, talent acquisition. Two front doors:
- **Web portal** (`resort-admin` guard, session) — HR/HOD/EXCOM/GM staff manage their resort.
- **Mobile app** (`api` guard, Passport token) — employees self-serve (apply leave, punch attendance, request island pass, etc.) and managers approve from their phone.
- **Wisdom AI** — a tier-gated HR chatbot addon (`app/Services/Wisdom`, OpenRouter + tool-calling), separate concern from the modules above. Company policy answers come from the resort's File Management folder named "Company Policies": `PolicyLibrary` sends those files (decrypted) to the Python AI service (`HRVMS-Wisdom-AI-Code`, `/policies/*`, a per-resort index next to the shared employment-law PDFs), kept in step by `ChildFileManagement` model events + hourly `wisdom:sync-policies`; WAI's `search_policy_documents` tool (offered to every tier) returns cited passages. WAI must not describe screens it wasn't told about — how-to answers come from `get_module_guide` (`ModuleGuide`: the user's own navbar via `Common::visibleResortMenu()`, shared with the navbar, + labels scraped from each menu page's blade view and its page-specific `resorts_assets/js` file); when the module is unclear WAI ends with `[[pick_module]]` and the chat shows the user's modules as chips. A few hand-verified paths/facts still live in `OpenRouterClient::systemPrompt()`. **Data questions go through the catalog, not new functions:** `config/wisdom_catalog.php` lists datasets (table, joins, fields with a sensitivity, resort + department scope columns); WAI calls `list_datasets` / `query_data` and `App\Services\Wisdom\DataCatalog` validates every name against the catalog and builds the query (query builder, bound values, `mysql_readonly`, resort filter on the base table and every join, `ctx.dept_ids` scoping, row/time limits). To make a new kind of question answerable, add a dataset or field there; never put AI text into SQL. **Who has WAI (decision 2026-11-13): ONLY the HR department's EXCOM (HR Director) and HOD** — `WisdomAccess::tier()` returns `full` for them and `none` for everyone else (other HR staff, GM, master admin, other departments, Finance). The other tiers below stay in code, dormant, for when access widens again (change `tier()` only). Tiers (`WisdomAccess`): `full` (HR) everything; `gm` no pay; `leader` (HOD/EXCOM/MGR outside HR & Finance) catalog only, own department via `ctx.dept_ids`, no pay/private, no resort-wide datasets, none of the older tools; `finance` (rank 7 or Finance-dept EXCOM/HOD) catalog only, `tier_datasets.finance` = payroll datasets + employee headcount, pay yes, names no. A child table without `resort_id` (payroll_reviews, training_participants) needs a `required` inner join to a resort-filtered parent — DataCatalog throws otherwise. Grievance/disciplinary stay out of the catalog (confidentiality). **Computed datasets** (`'source' => [ComputedDatasets::class, method]`, e.g. `leave_balances` from `Common::getEmployeeLeaveBalance`, liability = balance × basic MVR ÷ 30) cover values the app calculates in PHP; the source must apply resort + `dept_ids` itself, DataCatalog validates and aggregates in PHP. `query_data`'s tool description lists every dataset the user may use (so the model picks one without a `list_datasets` round). **Time:** `OpenRouterClient` allows 10 tool rounds within `TIME_BUDGET` 110 s, then `finalAnswer()` asks once more with no tools — never a canned "could not finish" reply; `WisdomChatController::chat` sets `set_time_limit(150)`, so prod nginx `fastcgi_read_timeout` must be ≥ 150s. **Accuracy rules learned (2026-11-13):** put business meaning in the catalog, not the prompt — status values and derived fields (`vacancies.is_open/applicant_count/days_past_start`, `expat_documents.can_work_legally/visa_days_left`, `immigration_renewals.blocks_work`); computed datasets must reuse the screen's own rules (expat_documents = XpactEmployeeController rules via `Common::visaNextDue` + the AI-extracted 'Other' document); headcount = active `employees`, never budget 'filled'. `wisdom_catalog.replaces_tools` hides overlapping legacy tools (incl. the SQL trio) from the model — they still execute. The system prompt carries the user's real menu (`ModuleGuide::menuSummary()`) as the only screen names allowed. `OpenRouterClient::$trace` records each tool call (name/args/size) for diagnosis. Each assistant turn stores its lookups (`lookups` in the session history, never sent to the UI) so follow-ups narrow the same data; identical repeat tool calls are refused (loop guard); `OPENROUTER_MAX_TOKENS` default 2000 (800 cut answers off). Coverage test set: the 19 module questions + follow-up chat in `docs/master-ai-intent-library.md` style — re-run them with the trace after changing the catalog. Model: gpt-oss-120b is cheap but misreads results; claude-haiku-5.5 tested far more accurate at ~$0.01–0.02/question (set `OPENROUTER_MODEL`; `OPENROUTER_REASONING_EFFORT` low suits reasoning models only). Tests: `tests/Feature/WisdomDataCatalogTest.php`.

## Architecture map

- **Routes**: `routes/resort_route.php` (web portal, `resort-admin` guard) and `routes/api.php` (mobile, `api` guard) are the two live route files. **`routes/resort_routemain.php` is dead code** — never `require`d anywhere, don't add routes there even if it looks like a plausible spot.
- **Controllers**: `app/Http/Controllers/Resorts/<Module>/...` for web portal (module folders: Accommodation, Leave, Payroll, People, Performance, TimeAndAttendance, Visa, Incident, GrievanceAndDisciplinery, Survey, Learning, TalentAcquisition, SOS, Support, FileManagment, ChatBoat, plus flat report controllers like `ProbationReportController.php`). `app/Http/Controllers/API/...` for mobile — organized by feature, not by mirroring the web folder structure (e.g. `LeaveController.php` in API also contains Island Pass HR/HOD view endpoints).
- **Multi-tenancy**: `resort_id` scoping on nearly every query. Never write a query against a tenant-scoped table without a `resort_id` filter.
- **Shared helper**: `app/Helpers/Common.php` — the household name for cross-cutting logic (currency formatting, approval-flow builders, geofence resolution, benefit grade resolution, AWS/attachment resolution, etc). When a fix applies to more than one controller, it almost always belongs here, not copy-pasted per caller.
- **`app/Helpers/StorageHelper.php`** — the ONLY correct way to read/write uploaded files. Never use raw `Storage::`, `->move()`, `public_path()`, `asset()`, or `URL::asset()` for anything tenant-uploaded. Prod runs `STORAGE_DRIVER=wasabi`; anything not routed through `StorageHelper` works locally and silently breaks in prod.
- **Sessions**: `EncryptCookies` → `AddQueuedCookiesToResponse` → `StartSession` run ONCE, in the global `$middleware` stack (`app/Http/Kernel.php`), and NOT in the `web`/`api` groups. Global is required: ~190 controllers read `Auth::guard(...)->user()` in `__construct`, and Laravel builds the controller before group middleware runs. With group-only it 500s ("resort_id on null"), which `actingAs()` tests hide. `SecurityRound2PeopleTest::test_a_browser_session_login_*` uses a real cookie. Never in both places: until 2026-11-10 it ran in both (audit run-3), so the session saved twice per request, the id rotated, an old id survived logout, the cookie skipped `EncryptCookies` and `->with()`/`->withErrors()` flashes were lost — older code renders errors on the response or returns JSON because of that; both patterns now work.
- **Super-admin console (`/admin`, `admin` guard)**: MFA (TOTP, `app/Helpers/Totp.php`) is mandatory via `AdminSecurity` middleware (also idle timeout, live status check, `admin_audit_logs`); dangerous routes carry `admin.reauth`. Passkeys/security keys (`PasskeyController`, `lbuchs/webauthn`, `admin_passkeys`) are an alternative second factor, bound to the request host. Path prefix comes from `ADMIN_ROUTE_PREFIX` env via `config('settings.route_prefix.admin')` — never hardcode `/admin`. Recovery: `php artisan admin:2fa-reset {email}`. Tests: `tests/Feature/SuperAdminSecurityTest.php`, `tests/Feature/AdminPasskeyTest.php`.
- **WAI Guide (in-app how-to)**: edge notch + panel + step card + ⌘K search, on every resort page via `resources/views/resorts/partials/wai-guide.blade.php` (included from the footer). Frontend only. All copy lives in `public/resorts_assets/js/wai-guide-content.js` (one guide per task, one `PG` entry per screen, keyed by route name; a step is `[title, help, route, selector-to-point-at, menu-to-open-first, how-it-is-done]` where how-it-is-done is `click` (default), `input`, `change` or `view`; the guide watches for it and moves to the next step by itself, and clicking a later step's control skips ahead. Use `''` as the route for record pages that have no fixed URL. Check selectors against the Blade/JS with the ids you can see in the view); the engine is `wai-guide.js`, loaded on first use by a tiny inline starter. When a screen, button label or approval chain changes, update its guide, then run `node tests/js/wai-guide-content.check.js` and `php artisan test --filter=WaiGuideContentTest`. Which guides a person sees: HR-department heads (`Common::isHR`) get all of them; everyone else gets the guides whose first screen is in their own sidebar menu (`wai-guide.blade.php` computes the menu pages their position may view, same rule as `MasterDashboardController::getMenuData`, and passes `data-menu`/`data-allowed`; a screen that isn't a menu page follows its module), with Show all guides as an escape hatch; the `who` labels only decide when no menu data is sent. A step whose control isn't on their screen is skipped with a note (at most 3 in a row). Only the Accommodation › Configuration setup guide is wired to live page events (`WAIGuide.done(...)` via `guideSync()` in `accommodation-config.js`).
- **`module_pages` table**: global (no `resort_id`), drives sidebar/menu labels, seeded via `database/seeders/ResortModulePagesSeeder.php`. Editing the seeder alone only affects fresh installs — a live/seeded label change needs a migration too.

## Hard invariants — do not violate

1. **DB changes go through migrations, never raw tinker mutations.** Tinker is for read-only verification (wrap any mutating test in `DB::beginTransaction()`/`DB::rollBack()`).
2. **Storage is disk-agnostic via `StorageHelper`.** No raw filesystem calls for uploads/attachments.
3. **Money**: `budget`/`salary`/cost aggregation tables store USD. `Common::formatCurrency($amount, 'USD')` converts stored-USD to the resort's display currency — correct for `employees.basic_salary`. For a value that IS whatever currency the user picked at submission time (e.g. `payroll_advance.currency`), use `Common::formatRequestCurrency()` instead — no conversion, display the literal currency stored. Don't mix these two up.
4. **FX rate**: MVR↔USD derives from `DollertoMVR` (currently 15.42); never multiply by a stored inverse rate.
5. **Department-scoped access**: every new list/dashboard must gate via `Common::hasFullDataAccess` + `getScopedDepartmentIds` — non-HR/GM HOD/XCOM only ever see their own department.
6. **Every active employee owns a categorized root folder** in `filemangement_systems` (maintained by an `Employee::created` hook + backfill migration) — don't build a parallel folder-creation path.
7. **Duplicate query paths per view are the norm, not the exception.** The same logical page is frequently served by 2-4 independent, near-identical controller methods (list AJAX endpoint, detail view, dashboard variant, HOD variant, mobile API variant). Before declaring any bug fixed, grep for sibling methods rendering the same page/data and fix all of them — fixing only the one in the reported URL is an incomplete fix.

## Before starting any task

1. Re-read this file. Confirm the task doesn't require changing something listed above as an invariant — if it seems to, stop and ask rather than quietly reinterpreting the rule.
2. Understand what module(s) the task actually touches. Grep first, don't assume — find every controller/view/route/API-endpoint that serves the reported page or data (per invariant #7).
3. Form a plan scoped ONLY to what was asked. Do not refactor, rename, restructure folders, or "clean up" adjacent code while you're in there. Do not touch a different module than the one the task concerns, even if you spot something else wrong nearby — note it to the user instead of fixing it unprompted.
4. Pick the smallest correct fix. Before writing new code: can an existing helper (`Common.php`, `StorageHelper`, etc.) already do this? Can the fix be a guard clause / one changed line instead of a new method? Don't add abstractions, config options, or generalized helpers for a problem that only has one caller today. Three similar lines beat a premature shared abstraction; a shared abstraction beats three copies of a real bug fix that all need to change together later.

## After finishing any task

1. Re-read every file you touched, in full, not just the diff hunk — confirm the change is complete and nothing adjacent broke.
2. Trace the actual data path end to end (form field → controller → DB column → the exact response/view the user will see) rather than assuming a plausible-looking fix is correct.
3. Verify against real data (`php -l`, then `php artisan tinker` against real records; wrap any DB mutation in a transaction and roll it back) — don't report a fix as done on code-inspection alone.
4. Confirm you didn't edit any file outside the scope of the request. If you found an unrelated bug while working, report it, don't fix it in the same pass unless asked.

## Before adding a notification feature

`Common::sendMobileNotification()`/`notifyEmployees()` guard against a wrong id-domain now
(logs + drops instead of silently failing — see `docs/notification-guardrails.md`), but the
guard only catches *that one* failure mode. Ask these six before shipping any new
"this should notify" feature — every one is a bug pattern that's actually happened here:

1. **Is `$sendto` actually `employees.id`?** Not `resort_admins.id` (the web-portal login
   identity — easy to reach for by accident since that's usually "the current user" in
   web-portal code), not a shopkeeper id, not anything else.
2. **Are you using `Common::notifyEmployees()`?** The one function that gets both channels
   (in-app + push) right with one call and no duplicate rows. Reach for it by default.
3. **Did you set `$requestId` and `$pageId`?** Without them the notification can't deep-link
   to the record it's about.
4. **Is the call wrapped in try/catch?** A notification failure should never roll back the
   business transaction it's attached to.
5. **If this is one side of an approval/request flow, does the other side notify too?** "The
   request pings someone, the decision doesn't" is the most common gap found in this codebase.
6. **If this is a create action, what happens on edit/cancel/delete?** Creation notifying
   while edit/cancel/delete don't is the second most common gap — a conscious decision, not
   an oversight.

## Business-model notes worth knowing before touching a module

- **Leave approval**: rank-based chain (Line Worker/Supervisor → reporting manager → HOD/EXCOM → GM), with HR/GM able to shortcut-approve. Clinic-staff (rank 12) stage can comment but never flips the leave to Rejected. No rank-override/skip-ahead exists anywhere.
- **Island Pass approval order is `HOD → HR → SM`** (3 steps) — enforced by execution order in the DB, not by the order rows were inserted.
- **Duty rosters**: geofence zone assignment is roster-level (one `duty_rosters` row = one employee's schedule block), not per-day or per-shift. It's a multi-select (JSON array of zone ids in `geofence_zone_id`, a `text` column — do not change it back to a scalar int).
- **Benefit Grid**: per-employee level override exists — an employee's own assigned level always wins over their rank's default grid; multiple grids can share a rank.
- **Time & Attendance**: `duty_roster_entries` = the plan (one row per rostered day, `CheckingOutTime` = shift end, `DayWiseTotalHours` = one day's hours); `parent_attendaces` = actual punches (no row = absent). Overtime lives in two places: `employee_overtimes` (created at checkout, approved on the T&A overtime screens) and `parent_attendaces.OverTime`/`OTStatus` (what payroll pays). Any status decision on `employee_overtimes` must call `Common::syncAttendanceOvertime()` or the approved OT is never paid. Payroll's day counts (paid day-offs and no-shows come from the roster, a present day's share of pay is time on shift ÷ shift length) go through `Common::payrollRosterContext/payrollDayMarks/payrollDayFraction`, shared by the Permanent run, Casual run and dashboard estimate — don't count `DayOff`/`Absent` attendance rows alone, nothing writes them.
- **Payroll lock flow**: draft → `sendForApproval` → Finance EXCOM → HR EXCOM → GM; the GM's approval **locks automatically** in the same transaction (`PayrollController::finalizeAndLockPayroll`, marks recovery schedules/shop payments Paid). There is no manual lock; `saveSummaryToPayroll` only finalizes legacy runs stuck at `approved`. Each approve step stores a frozen signature on `payroll_approvals`.
- **TA interviews**: `applicant_inter_view_details.Status` is a plain string now (Pending Review → Invitation Sent → Slot Booked | Invitation Rejected | Cancelled). Reschedule reuses the same row; "remove from shortlist" = reject + cancel open slots. Closing a vacancy sets `vacancies.status='Closed'` and expires its `application_links` (previous expiry kept in `expiry_before_close`). `application_links.Old_ExpiryDate` is a DATE column holding only the single previous expiry (set by extend-expiry); nothing reads it. Extending a Closed vacancy's link is refused.
